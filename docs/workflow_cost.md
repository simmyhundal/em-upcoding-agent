# Workflow cost on the stored release 1 runs (issue 91)

[Back to the README](../README.md)

Generated by `python eval/workflow_cost_91.py` from the #61 run folders (13 datasets, workflow arms W2.0 and W2.1). Free: the script replaces every API call with an error, so anything not already in a run's response cache would stop it. The 13 datasets are development data now (seen in #61), so these numbers can guide release 2 but cannot confirm it.

## Summary

- **Measured on the stored runs, a v2.1-style workflow arm costs $0.255 per 216-doctor dataset; with rules 2.2 and no LLM judge it would have cost $0.014** (94% less), with the same upcoders and honest doctors called (40 and 1 over the 13 runs) and 0 leanings changed.
- Implemented behind the 2.2 flag: rules 2.2 (`case_summary.py --v22`) and no LLM judge (`llm_judge=False`). The frozen v2.0 and v2.1 paths are unchanged: every stored #61 workflow summary regenerates identically (section 1).
- Measured but not implemented: shorter cards and lower effort (they change the prompt, so only a paid run can show their effect, and little is left to save), the top 5% list (about as long as the suspicion >= 5 list on these datasets, and a screen decision for #88 and #90), a shared cache (no overlap). Every call already went through the Batch API.

## 5. Evidence card size by section (measured; not changed)

On the 115 stored v2.1 model calls the prompt averaged 4,031 input tokens; 2.06 characters per token (system prompt plus user prompt, measured against the stored usage). The system prompt is about 1,198 tokens.

Input is $0.93 of the $1.87 writer cost on these runs. The three claim-sample tables are the largest part. Share of the model's interpretations (the code-written examples left out) that quote at least one claim ID from each table: claims_99215_low_complexity 86%, claims_99215_high_complexity 12%, claims_other_codes 2%. So the high-complexity and other-codes tables, about a quarter of the input, are the ones to cut first. Cutting a table changes every prompt, so the cache cannot show whether any leaning changes: that needs a paid smoke run, and with rules 2.2 only about 1 call per dataset is left to save on. Not implemented.

## 6. Output tokens (measured; not changed)

The writer returned 1,408 characters of JSON per call (mostly English prose, so roughly 352 tokens at about 4 characters per token; the 2.06 ratio above is for ID-heavy input) and was billed 816 output tokens on average; the difference is most likely the model's thinking at `effort` medium (an estimate: the usage log does not split it). Output is $0.94 of the $1.87 writer cost. `effort` low would cut it, but it is part of the cache key and may change leanings, so it needs a paid smoke run; with rules 2.2 the saving is a few cents per dataset. Not implemented.

## 7. Batch API everywhere

Stored #61 workflow calls by route: batch 624. Every writer and judge call went through the Batch API at half price. `llm.sync_call` (full price) runs only for `--sync`, for a batch request that errored, expired or was refused (a refusal needs the server-side fallback, which batches do not allow), or for a request a batch did not return.

## 8. A response cache shared across arms

Writer prompts of W2.1 identical to a W2.0 prompt on the same dataset: 0 of 115. Judge prompts: 0 of 191. The arms see different charts (office 2.0 against 2.1) and different card contents, so a shared cache would not have saved anything. Not a lever.
