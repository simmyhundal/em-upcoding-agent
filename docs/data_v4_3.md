# Data 4.3: busier honest days, varied charts and a more realistic office (data card)

[Back to the README](../README.md) · [files and fields](data_fields.md) · [data 4.2](data_v4_2.md) · [versions](versioning.md) · [seed roles](seeds.md) · [release 4.3 plan](release_v43_plan.md)

**What this page is.** The public description of synthetic data version 4.3, for an analyst who builds a workflow or an agent on it: what changed from data 4.2 in the files an analyst sees, which mechanisms exist (in plain words), the new answer-key fields the evaluation reads, the build command and the seed pools. It deliberately gives **no** rates, thresholds, overlaps or statistics: data 4.3 was built by a separate session so that the arms are developed without knowing how the signals were made (the "sealed data design" in [the release process](process.md)). The generator's design page stays sealed until the release's test is done and then moves next to this page. Issues: [#197](https://github.com/simmyhundal/em-upcoding-agent/issues/197), [#220](https://github.com/simmyhundal/em-upcoding-agent/issues/220), [#201](https://github.com/simmyhundal/em-upcoding-agent/issues/201), [#137](https://github.com/simmyhundal/em-upcoding-agent/issues/137), [#144](https://github.com/simmyhundal/em-upcoding-agent/issues/144).

In one paragraph: data 4.2's world (no planted upcoder, a continuous true rate for every provider, some providers also billing for visits that never happened or unbundling) is kept. What is new is that the easy signals of data 4.2 get honest look-alikes. Honest practices can have very busy days, so a [volume screen](concepts/volume-screen.md "flag providers by claims per day from claims alone") meets real crowding as well as fraud. Visits that never happened can be thinly spread as well as piled onto a few days. Diagnosis codes can make a panel look sicker or healthier than it is. Charts vary the way real documentation does. And a practice asked for a chart of a visit that never happened may send one instead of answering "no record".

## Build it
```bash
python3 src/generate_v2.py OUT --seed N --data-version 4.3 --answer-key KEY      # KEY must be outside OUT
python3 eval/make_d43_dev.py [--first N] [seed ...]                               # development seeds as code runs d43_<seed> (data, view, screens, control sample)
```
Optional: `--holdout-family NAME` (repeatable) switches one mechanism family off (below); `--years Y` spreads the data over Y calendar years (default 1; volume scales with it). The data 2.2 options (`--group-billing`, `--rendering-omitted-share`, defect shares, `--control-totals`) work as in data 4.2.

**Seed pools** (`eval/dev_pool_v43.py`; record their roles in the [seed registry](seeds.md) before use): development `1003 + 41j` (100 seeds), confirm `1004 + 41j` (100, built only with `--confirm`), test `6003 + 41j` (10) and reserved `7003 + 41j` (10), never generated by the build script. Data 4.3 seed `s` and data 4.2 seed `s` are different datasets with different random streams.

**Reproducibility.** Data 2.0, 2.1, 2.2, 4.0 and 4.2 and offices 2.0, 2.1 and 4.2 reproduce byte for byte (`tests/test_generator_regression.py`, `tests/test_d40_regression.py`, `tests/test_d42_regression.py`, hashes taken before data 4.3 existed). A data 4.3 build is deterministic per seed, and with every data 4.3 option off it writes the same files as data 4.2 (`tests/test_data_v43.py`).

## What an analyst sees in the files
Same files and the same columns as data 4.2 ([files and fields](data_fields.md)); the values behave differently.

| File | What is different from data 4.2 |
|---|---|
| `claims_header.csv` | Busier days for some honest providers. Some original claims carry a batch date instead of the date of service; some of those are later replaced by a correction (`claim_frequency` 7) with the true date. Diagnosis lists can be longer (codes the member's other claims do not support) or shorter (only the first one or two conditions) than the patient's conditions. Patients of an absent colleague appear under the provider who covered. |
| `claim_lines.csv` | The lab or test line is less tied to the visit's level. Some practices send tests to an outside lab, so the test is in the note but not on the visit's claim. Some upcoded visits carry a test they did not need. |
| `members.csv`, `remittance.csv`, `providers.csv`, `reference/*` | Unchanged in form. |
| the chart (an office's answer) | Same columns as office 4.2. An element level can disagree with the note text or read as minimal although the note says more. Time can be rounded, or stated in the note only as a range, with `documented_minutes` blank and `time_statement` = `range`. Signatures can be late; a note can carry an addendum (`auth_status` = `amended`, `signed_date` = the amendment's date). Some honest templates add boilerplate that documents more than the visit needed. A copied-forward note can list a problem that is not on this claim. |
| `records/office_chart_plan.csv`, `records/office_profiles.csv` | **New, simulator-side only** (never in the view, never shown to an arm): per-claim settings and per-practice response profiles read by office 4.3. |

## The mechanisms, in plain words
**Legitimate high volume** (honest providers; their visits happened and are billed at the right level):
- *Mid-level visits under the physician's number*: a nurse practitioner's or physician assistant's visits billed under the supervising physician.
- *Coverage*: a provider sees an absent colleague's patients for a block of days; the absent colleague has no visits then.
- *Short clinic week*: a provider works only some weekdays, so the same volume falls on fewer days.
- *Quick-visit clinic days*: a few days with many short, low-level visits (a vaccine or screening clinic).
- *Batched service dates*: a billing error dates a batch of visits on one day; some are corrected later.

**Suspicious volume** (visits that never happened; their whole paid amount is overpaid), drawn so that it overlaps the honest busy days instead of standing far above them:
- *Ghost panel*: repeated visits on a few members of the provider's panel (data 4.2's kind).
- *Spike days*: extra visits added on a few days.
- *Padded days*: a few extra visits added on many ordinary days.

**Charts for visits that never happened.** Some providers who bill for visits that never happened produce a chart when asked, sometimes only after the claim is asked about again. Such a chart looks like any other chart: same columns, no marker; it may or may not show the signs real reconstructed notes sometimes have (late signature, late creation in the audit trail, pasted text), and honest charts show those signs too. When a provider cannot or does not produce one, office 4.3 still answers "no record" ([records not provided](concepts/records-not-provided.md "a sampled claim with no chart counts as overpaid under score 4.2")).

**Claims-based confounders**: diagnosis inflation (codes added that the member does not have; raises the derived risk score) and sparse diagnosis coding (an honest provider lists few codes; lowers it).

**Lab or test line** (issue 144): a weaker link to the visit's true complexity, practice-level test habits, outside labs, unneeded tests on upcoded visits.

**Calibration** (issue 137): recalibrated habit shares (the habits keep data 4.0's meaning), a per-provider share of visits with time recorded, an optional multi-year range with drift across it.

**Office 4.3** (`provider_sim.Office(..., version="4.3")`; offices 2.0, 2.1 and 4.2 are unchanged): office 4.2 plus a chart for some visits that never happened, charts signed when the request arrives (a `signed_date` after the request), a held-back note that comes back changed on the next answer (`auth_status` = `amended`), coder disagreement that depends on the case instead of one flat rate, and a response behaviour (cooperative, slow, sloppy, evasive) that belongs to the practice and is often shared within a group. The plan side sees what it saw with office 4.2: statuses, deficiencies, usable charts, days and rounds. Note: `src/fwa_lane.py` (workflow v4.2's lane) builds its own office at version 4.2, which on data 4.3 still answers "no record" for every visit that never happened; to see data 4.3's office behaviour an arm's office must be version 4.3. The same holds for agent v5.2, whose tools (`src/agent_tools.py`) build office 4.2.

## Held-out mechanism families
Any family below can be switched off with `--holdout-family NAME` (or `holdout_families=(...)` in `generate_v2.build`), so a whole mechanism can be kept out of development data and used only in a held-out test. The families switched off are recorded in the answer key. Which family, if any, is held out for a release is a decision for the release plan, made before the data is built.

`shared_npi`, `coverage`, `compressed_schedule`, `quick_visit_days`, `date_batching` (legitimate volume); `ghost_panel`, `spike_days`, `padded_days`, `unbundling` (fraud, waste and abuse); `fabricated_charts`; `diagnosis_inflation`, `sparse_diagnoses`; `lab_realism`, `unneeded_tests`; `chart_variability`, `template_boilerplate`, `late_amended`, `case_coder_disagreement`; `office_profiles`.

## The answer key (evaluation only)
`eval/answer_key/ground_truth_v2_<code>.json` (gitignored). Every field data 4.2's scorer, oracle and metrics read is kept with the same meaning (`providers[pid]`: `net_rate`, `true_overpay_level_net`, `true_overpay_level_gross`, `true_overpay_fwa` = {`not_rendered`, `impossible_days`, `unbundling`}, `true_overpay_total`, `habit`, `intent`; top level: `fraud_claims` = {claim_id: kind}, `justified_cpt_by_claim`). There is no `role` or other binary label. Phantom visits on padded days count as `not_rendered` in `fraud_claims` and in the dollars; spike-day visits as `impossible_days`.

New per-provider fields:

| Field | Meaning |
|---|---|
| `fwa_mechanisms` | `{ghost_panel, spike_days, padded_days, unbundling}`: which fraud, waste and abuse mechanisms the provider uses |
| `fwa_mechanism_claims` | number of never-rendered claims by mechanism (`ghost_panel`, `spike_days`, `padded_days`) |
| `fabricates_charts`, `fabricated_chart_claims` | whether the provider produces charts for visits that never happened when asked; how many of its never-rendered claims have such a chart |
| `legit_volume` | `{shared_npi, covers_colleague, absent_covered, compressed_schedule, quick_visit_days, date_batching}`: the legitimate reasons for volume that apply to the provider |
| `extra_rendered_visits` | real visits added by `shared_npi`, `coverage` (patients of an absent colleague) and `quick_visit_days` |
| `date_batched_claims`, `date_corrections` | how many of its original claims carry a batch date; how many of those a correction replaced |
| `dx_coding` | `inflated`, `sparse` or `typical` diagnosis coding |
| `in_house_lab`, `orders_unneeded_tests`, `unneeded_test_paid` | whether its tests are billed on the visit's claim; whether it adds unneeded tests to upcoded visits; what those tests were paid (not part of `true_overpay_total`) |
| `time_recording_share` | the share of its visits whose total time is recorded |
| `office_behavior` | its practice's response behaviour in office 4.3 |
| `intent` | adds `fabricated_charts`, `diagnosis_inflation`, `unneeded_tests`; `not_rendered` is also true for padded days |

New top-level fields: `fraud_claim_mechanism` = {claim_id: mechanism} for every never-rendered claim; `fabricated_chart_claims` = the claims that have a produced chart; `date_batched_claims` = {claim_id: true date of service}; `holdout_families`; `years`; `config_profile` and `config_hash` (identify the generator settings; data 4.2's `parameters` block is not written).

## What is still easier by construction
Charts and the truth come from the same generator, so the level truth is defined by the same complexity the chart elements are read from. Every claim is an E/M office visit of one specialty in one state. The office is a simulation; its response tables are assumptions that have not been checked against published records-request response rates. Fraud kinds without a volume or chart signal (ghost members, unbundling beyond data 4.2's) and free-text notes are later versions (data 4.4).
