# Data-quality pre-flight (issue 81)

[Back to the README](../README.md)

Generated by `python eval/grade_data_quality.py --write`. The pre-flight (`src/data_quality.py`) runs once per data load, before any screen, on the delivered plan tables; it never reads an answer key. This page grades it against the defects injected into data 2.2 ([data_v2_2.md](data_v2_2.md), issue 80).

## What it checks

| Check | Warns when | Blocks when |
|---|---|---|
| Control totals | a month's claims or paid dollars differ from the plan's control totals by more than 0.1% | more than 5% in any month |
| E/M mix | total variation distance from the Family Practice benchmark above 0.15 (informational) | never |
| Diagnosis codes per claim | a month's maximum is below the extract's width of 6 and 15% or more of its claims sit at that maximum (suspected truncation) | never |
| Rendering NPI | blanks under an organizational biller exceed 0.5% of claims (single-clinician blanks fall back to billing and are only reported) | above 20% |
| Member join | below 99.9% join to eligibility | below 90% |
| Duplicates | more than 0.4% of paid claims repeat another claim's member, date, biller, diagnoses and E/M line | never |
| Replacement and void chains | any replacement or void whose original is missing | never |
| Immature recent months | a latest month holds under 70% of a typical earlier month | never |

A warning does not stop the run; a block does (workflow: `flagging.py --preflight` exits non-zero unless told to continue). Thresholds were set by looking at the clean datasets below, not the defect dataset: the natural duplicate rate in clean synthetic data is about 0.1%, so the duplicate threshold sits at 0.4%.

## How findings are held

Per-provider flags carry the sentence a reviewer reads next to a finding (for example "38% of the claims billed by this provider's group lacked a rendering NPI"). `data_quality.hold_decision` turns them into a policy: an affected provider's upcoding finding needs chart evidence (at least 8 charts received), otherwise it is held, and every affected finding carries the data caveat and is marked low confidence. Truncation-suspect months affect any provider with 25% or more of its claims in those months. **Workflow:** `src/flagging.py --preflight V2_DIR` writes the report next to the flagged list and adds a `data_quality` column. **Agent v3.2:** the read-only `data_quality` tool returns the global flags and, for a provider, its flags; `flag_data_issue` records a concern for a person to raise with the plan and can hold findings; `submit_findings` refuses an upcoding leaning for a held provider without chart evidence. Neither stream requests data from the plan.

## Limits

- Graded on one injected dataset and three clean ones, all synthetic and all seed 42 or 1414; thresholds were not tuned on the defect dataset but the defects were chosen to be detectable in kind. A real extract has defects nobody has listed.
- The duplicate check can only see exact repeats; a real double load with a changed field would pass. Truncation is detected only when the cap sits below the extract's width and affects a visible share of claims, and a cap applied to every month is flagged on its own pile-up (no month to compare against).
- The claims-lag check is a volume ratio; it is not tested against a real lag (issue 78 is not built).
- The agent's hold policy is built and unit tested offline; no model run used it, so how an agent uses these tools is untested.
