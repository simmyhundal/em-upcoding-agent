# Agent v5.1 (A5.1): the model-driven reviewer, set up to follow workflow v4.1

[Back to the README](../README.md) · [workflow v4.1 freeze](w41_freeze.md) · [workflow v4.1 result](w41_fresh_result.md) · [agent tools](agent_tools.md) · [versioning](versioning.md) · [concepts](concepts/README.md)

**What this page is.** This project builds two reviewers for suspected E/M upcoding on synthetic claims: a [workflow](concepts/workflow-and-agent.md "Code fixes the order of the steps") and an [agent](concepts/workflow-and-agent.md "A model chooses its own steps within caps"). Workflow v4.1 was frozen first; this page describes agent v5.1, which gives the agent the same three behaviours through its tools so the two can be compared fairly. Words in links open a short page that explains them. Score 4.0, data 4.0. Built and tested for free. **Not run on any fresh seed.** The paid run needs Simmy's OK after the estimate below. (It has since been run once; see [the result](a51_fresh_result.md).)

## What changed from agent v5.0
`Environment(version="5.1")`, prompt `SYSTEM_51`, `eval/run_agent.py --version 5.1`. Agent v5.0 and v3.x are unchanged (their tests pass). A5.1 copies three things workflow v4.1 added to workflow v4.0:
1. **A [shortlist](concepts/shortlist.md "The few providers at the top of the screen's ranking that the system takes further") of four.** `screen_providers` (method `eb_upper_t`) still shows the top 10%, but the [request recommendation](concepts/request-recommendation.md "ASK or SKIP: is asking for charts expected to pay for itself?") is ASK or SKIP only for the first 4 rows. Every other row is SKIP, and the result carries a `list_note`. The model behind the recommendation sees the same row as in the workflow (the rank is kept). [Triage](concepts/triage.md "The analyst's first look at a shortlisted provider, priced at about $13") costs about $13 for each provider the agent submits a finding for; the workflow triages all four shortlisted providers, the agent only those it asked.
2. **A looser chart test.** [Chart review](concepts/chart-review.md "The tool that reads returned charts and decides whether they support the billing") (`hybrid_review`) uses rules 4.0 with the options of hypothesis H17 of the [workflow development loop](w_loop_v4.md): at least 5 documented 99214 and 99215 charts, an unsupported share of at least 10%, alpha 0.20. The writing check in `submit_findings` accepts the same test.
3. **A second sample for [borderline cases](concepts/borderline-case.md "Best estimate well above the cost of a demand, but the conservative estimate below it").** For a provider that chart review calls upcoding, the result carries a [demand check](concepts/demand-check.md "The recovery economics next to the evidence"): the payer's best estimate of the recovery, its [conservative estimate](concepts/conservative-estimate.md "The 90% lower bound: the amount we are 90% confident is at least owed"), the cost of a demand ($276) and whether the case is borderline (code: `near_miss`). Borderline means the best estimate is at least twice that cost while the conservative estimate is below it. Then the advice is to request 30 more random charts, once, follow up on any deficiency, run chart review again and stop. `request_records` enforces this: a second random request is refused unless the provider was called upcoding and is a borderline case, it is accepted once only, and a request of more than 30 charts is refused. After it, the earlier review is stale, so `submit_findings` demands a new chart review. `estimate_overpayment` also returns the demand check.

Kept from v5.0: the [break-even rule](concepts/break-even-rule.md "No demand when the conservative recovery is below the cost of a demand") in `submit_findings` (a call whose conservative estimate is below the cost of a demand is withdrawn to inconclusive), the [hard rule](concepts/hard-rule.md "The model cannot override an upcoding call that the rules and the chart test both support, without naming a fact the rules cannot see") of v3.5, the [no-more-requests advice](concepts/no-more-requests.md "After the first sample and its follow-up, ask for nothing more") after the first sample (no targeted request, no audit trail), and the style repair. Everything the agent sees is payer-visible: the estimate uses only claims and the charts the office sent (`src/recovery_40.py`); tests check that no answer key file is opened and no role appears in a tool result.

## Does the agent match workflow v4.1? (free, development seeds only)
`eval/agent51_parity.py` runs a *scripted agent* (a stand-in whose steps are written in code to follow the advice exactly, so the tools can be checked without paying for a model) that follows the advice (ask where ASK, 30 random charts and one follow-up, chart review, a second request for each borderline case, chart review again, submit the leanings). It runs on the 20 development seeds of batches 5 and 6 (3630 to 4029) and is compared with the stored workflow run `wlh23_n4_<seed>`. No model is called.

| Check | Same on |
|---|---|
| Providers asked | 20 of 20 seeds |
| Providers given the second sample | 19 of 20 seeds |
| Providers called upcoding (after the break-even rule) | 19 of 20 seeds |
| Score 4.0, agent scored with the workflow's four shortlisted providers | 19 of 20 seeds (to the cent) |

Mean score per seed: workflow v4.1 +$1,381; scripted agent with the same four shortlisted +$1,405; scripted agent with its natural triage (a finding only for the providers it asked) +$1,430. The gap in the natural column is the triage of shortlisted providers that were not asked ($13 each); it favours the agent by construction.

The one seed that differs is 4029. The scripted agent gave provider 1000000056 a second sample and the workflow did not, and the workflow's final score there is $487 lower. What was observed: in the workflow's first pass this provider's summary read inconclusive (the chart test did not fire); after another provider's second sample rewrote the view, the rebuilt summary read upcoding (6 of 27 documented charts below the billed level, p = 0.199, under alpha 0.20), and the break-even rule then withdrew it. The workflow decides second samples from the first pass; the agent sees the second reading. I did not trace why the two passes differ (the first-pass p value and peer rate were not measured). It is a borderline case of the loosened test. This is near parity, not parity, as for v5.0.

## The paid path was checked on development seeds
The comparison above was measured on the live environment. The paid runner scores a run another way: `run_agent.main` writes `audit.jsonl`, `judge_agent_runs.main` replays it against a fresh office to rebuild the charts, and `score_40.from_run` scores the rebuilt view. `eval/agent51_replay_check.py` feeds the scripted agent's recorded tool calls through the real loop with a stub client (no API call), including a refused second second sample and a refused request of 80 charts, then scores the stored run. Result on seeds 3672 (one second sample) and 4008 (two): the stored-path score equals the live score to the cent, with equal rounds, charts and demands. Two details made this work: the second sample is refused when it asks for more than 30 charts (not cut, so the logged arguments are what the office received), and the replay skips `request_records` calls that the environment refused. The advice log records an second sample as its own action, `EXT`, which counts as following the advice.

## Cost estimate for one run on the ten test seeds (not run)
Basis: A5.0's recorded usage on the same ten seeds, $1.135 in all (experiments `fra50_*`; $0.08 to $0.15 per run, 4 to 6 turns, 5 to 16 tool calls; Opus 5.5, low effort).
- Prompt and longer tool results: about +$0.05 for ten runs (about 450 more prompt tokens, a `demand_check` of about 150 tokens per call).
- Second samples: the scripted agent gave a second sample to 13 providers in 20 development seeds, so about 6 or 7 in ten seeds. Each adds about three turns and about 3,500 tokens of charts to the cached context: about $0.085, so about $0.55.
- **Expected total: about $1.7.** Plausible range $1.3 (no second sample) to $3 (two second samples on every seed). The runner stops at a $4 batch cap, and each run has a $1 cap.

## What is not done
- No paid run. `eval/run_v51_fresh_agent.py` refuses without `--approved`. It runs A5.1 once on 5555 to 6464 (second use of those seeds for the agent line, as for W4.1) and writes `experiments/v51_fresh_results.json`. The second fresh pool (6565 to 7474) is untouched.
- The parity check uses a scripted agent. A real model may ignore the advice, so the agent's score can differ from the workflow's (A5.0 was $380 per seed above W4.0 with equal found).
- The shortlist of four and the second sample are mirrored by advice and one hard rule (the second-sample gate). The agent can still ask a provider outside the shortlist (the records budget is 22, as for A5.0); this costs it staff hours under score 4.0 and is logged.
